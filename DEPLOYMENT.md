# Next.js + Vercel + Neon

Production: **https://flytris.net**. The project uses Next.js 16.3.5 / React 19.3.0
on Node.js 24. The App Router server-renders the page, metadata and canonical URL.
`robots.txt` and `sitemap.xml` are generated by Next.js. The game and Three.js run
in cached, versioned browser assets; no database credentials enter those assets.

## Deployment settings

- Root directory: repository root (`.`).
- Framework: **Next.js**. Build: `npm run build`. Output: **`.next`** or framework
  default. Remove any old dashboard override pointing to `public`.
- Node.js: **24.x**. Install: `npm install` (a package lock is committed).
- Environment: server-only `DATABASE_URL` pointing at Neon. Keep Production and
  Preview databases separate. Ranked API access requires an allowed custom domain;
  arbitrary `*.vercel.app` origins are intentionally denied.

The committed `vercel.json` selects Next.js and `.next`. The build prepares the
SSR shell and game assets, runs the idempotent schemas in `db/001_matches.sql`,
`002_request_limits.sql` and `003_checkpoints.sql` when Neon is configured, builds
Next.js, and scans public/client assets for accidental database credentials.
Migration errors fail the build. Missing Neon leaves production scores unavailable;
Vercel never silently falls back to an ephemeral SQLite database.

`/api/scores` is now `app/api/scores/route.js`. `/report.html` and `/index.html`
redirect to `/`. Per-request CSP nonces authorize Next.js hydration and the game
scripts. Production does not permit script `unsafe-inline` or `unsafe-eval`.
Nonce-bearing HTML is dynamic and is not CDN cached; game assets are separate.

## Local development

```sh
npm install
npm run dev
npm run test:server
npm run build
```

Open `http://127.0.0.1:8765`. Development initializes persistent SQLite at
`.local/leaderboard.sqlite`. This file, build outputs and credentials are ignored
by Git. `npm run start` serves a production build; production mode requires Neon.
`npm run build:standalone` retains the self-contained research report workflow.

## Ranked match lifecycle

Ranked presets last **two minutes** at 800/500/250 ms gravity for Easy/Medium/Hard.
The human and verification clock use 50 ms simulation steps. The fly advances
one trained 50 ms step every 100 ms on Medium (half speed), or every 50 ms on
Easy and Hard. Medium therefore has 1,000 ms effective fly gravity and a
1-second fly landing delay; human gravity remains 500 ms.

1. `start` assigns an opaque match ID, private token, preset, server timestamp and
   a fly run from the committed pool. A new row deliberately has `completed_at`
   and every result column set to NULL. It is a session, not a leaderboard entry.
2. Every ten simulated seconds, the browser pauses and submits an ordered input
   batch. The server replays the human's controls and the selected fly recording,
   checks timing, and atomically advances the checkpoint revision. Same-batch
   retries return the existing receipt; altered or out-of-order batches fail.
3. `finish` is accepted only after a verified terminal state. The server derives
   both scores, winner, reason and elapsed time, then writes all result columns in
   one update with its own completion timestamp. Claimed results, if supplied,
   must agree with verification. Invalid input returns a truthful 400 response;
   token, sequencing and rate failures use 403, 409 and 429 as appropriate.
4. Both scores initially use `anonymous`. A valid match token can set a name of
   up to 60 characters for one hour after completion. Names are plain text.

Only `rules_version=5` (checkpoint-verified matches with half-speed Medium) enters current leaderboards.
Earlier rows, including version 4 matches and unfinished sessions, remain intact
but do not enter the current leaderboard. No database migration is required.
Ranking uses lines, pieces, then earlier completion time. Rolling 24-hour, 7-day,
30-day and overall windows use server completion timestamps. Chart totals include
all matching verified matches; the three difficulty lists show ten human scores,
each paired with that match's fly score. Names are public and unauthenticated.

## Updating the opponent

The trained checkpoint is unchanged. Ranked mode selects from nine offline fly
runs: three seeds at each difficulty. Practice uses fresh browser inference.
Generate a new pool with `npm run pool:build` after updating the model, review it,
and commit `site-data/ranked-pool.json`. This is an explicit offline operation,
not work repeated during builds or on every visitor's request. A pool/model
change invalidates old in-progress ranked sessions; the server rejects mismatches.

Training/evaluation snapshots still use `evaluate-falling.cjs` and
`integrate-falling.cjs`. Historical three-minute measurements remain accurate and
separate from current match duration. The physics and trained weights are unchanged; Medium plays the fly simulation
at half speed.
